# ESA 评测任务构造原则

版本：2.0。日期：2026-11-03。执行合同见[参考验证规格](<esa-solvability-spec.md>)，任务清单见[构造方案](<esa-benchmark-plan.md>)。

## 任务定义

1. 用户指令描述明确的目标和业务限制。评分要求不能依赖未公开的产品策略。
2. 任务环境使用固定资料、固定时钟和独立会话。开放工具必须提供完成任务所需的信息。
3. 题目域、交互类型与难度分别记录。七项验收任务用于检查机制，模型难度需要独立校准。
4. 边界任务必须检查全部开放能力的替代实现。删除一个工具不能自动证明任务不可满足。

## 原生 Oracle 与文件边界

5. 所有活动任务必须兼容 Harbor 原生 `OracleAgent`，并提供标准 `solution/solve.sh` 入口。参考程序与辅助 Python 文件放在 `solution/`，评分与错误答案测试放在 `tests/`。
6. Oracle 仅在原生执行阶段接收 `solution/`。运行入口只读取环境初态与参考程序，并访问实际 MCP。verifier 在评分阶段接收 `tests/`。普通模型不得接收参考解或评分答案。
7. 环境镜像仅复制初态。任务不把参考程序、错误答案测试或 rubric 编入镜像。
8. 参考执行器、Oracle 运行入口和任务评分副本必须与共享实现一致。修改共享实现后运行[同步脚本](<../scripts/sync-task-scorers.py>)，再执行 `--check`。

## 信息来源与独立评分

9. 每题提供 `solve(ctx)`、独立 rubric 和非空 `CASES`。参考程序只能使用已交付的用户输入、模型可见工具定义和实际工具返回。
10. 作者根据题意独立填写评分目标。禁止从参考终态自动生成标准答案。
11. 源代码检查用于防止误读隐藏信息。参考程序属于可信作者代码，信息来源与语义仍需人工审核。
12. 草稿的参考程序与错误测试必须完成后才能认证。空的 `CASES` 在创建 HTTP 会话前被拒绝。

## 参考预检与原生验收

13. 正式模型运行前，在本次实际部署环境执行参考、已知合法替代解和错误解。每个程序使用独立会话。
14. 参考预检与正式 verifier 共用 `evaluate`。Oracle 只保存真实执行证据，由同一个正式 verifier 评分。
15. 正例必须正常执行并通过全部必需条件。负例必须正常结束，并被有效评分拒绝。程序异常、连接故障与证据缺失不能作为错误答案测试成功的依据。
16. 证据记录输入、执行源码、实现、数据和评分摘要。各程序变体的初始与最终环境身份必须一致。内容发生变化或指纹缺失时拒绝认证。
17. 参考入口遵守 runtime 的 `call_id` 唯一性约束，执行设置期限，禁止覆盖参考入口或绕过验证进程。
18. 新增或修改任务后，必须使用[原生 Oracle 配置](<../configs/jobs/esa-oracle-acceptance.yaml>)执行实际 Docker 验收。自定义 Agent 或临时 HTTP 预检不能替代此项验收。新增任务同时加入[benchmark 配置](<../configs/bench/esa.yaml>)和原生验收配置。

## 评分

19. 使用独立目标状态与业务约束判定结果。`tool_checks` 接受合法替代工具；没有业务顺序要求时不指定工具顺序。
20. 禁止状态修改、禁止工具和过程违规使任务总分归零。修改后恢复仍属于违规。
21. 必需条件不受零权重影响。加权分用于诊断，`passed` 表示所有必需条件通过。
22. 正则只检查明确硬特征。自然语言语义由人工审核，并在需要时使用经过校准的 judge。
23. 程序异常、证据收集或清理错误、必需 judge 不可用、未知规则和必要证据缺失使评分无效且总分为零。不得静默删除评分维度或改变权重。
24. Oracle 达到目标状态后发生程序异常，也必须被正式 verifier 拒绝。[失败回归脚本](<../scripts/test-oracle-failure.py>)验证该条件。

## 交互与故障

25. 固定多轮消息共享状态与对话历史。澄清题使用确定性 `user_script`，只有匹配的助手问题才能获得后续用户回答。
26. 澄清题检查确认前未执行、确认后终态正确及对应轮次回复。未完成声明的澄清分支时评分失败。
27. 工具故障必须真实注入并被观察。响应丢失需要已提交事件证明，普通连接错误不能替代此证据。
28. 只读操作可以按规则重试。写入恢复使用幂等机制或查询确认，不重复不确定的副作用。同标识幂等恢复由独立环境测试检查。

## 审核与报告

29. 验证通过证明指定环境中的已验证参考解存在。该结果不能排除指令歧义、未覆盖路径、评分缺陷或模型运行期故障。
30. 人工审核检查指令、信息来源、判分点和合法替代解。启用语义 judge 时增加正确与错误答案校准。
31. 模型失败保留完整轨迹，检查工具、环境和评分后判定责任。存在环境或评分缺陷的试验不用于正常模型比较。
32. 集合指标使用必需条件通过率，分别报告业务领域、交互类型和失败类别。重复运行时区分全部成功与至少一次成功。
