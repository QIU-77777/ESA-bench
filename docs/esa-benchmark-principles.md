## 0. 定位与决策记录

**评测目标**：测出座舱 Agent「能不能做对、该不该做、做不了怎么说」——M1 任务完成、M2 澄清合理性、M3 能力边界与幻觉控制、M4 策略与最小副作用。

**benchmark 定位**：能力覆盖型，不是体验仿真型。题材由设计矩阵推演（决策 D1），场景配比按域×层均衡分配，不按真实使用频率加权。**解释力边界**：结论回答「能力短板在哪」，不回答「真实用户体验分布如何」。

### 已拍板决策

| # | 决策点 | 结论 | 代价（明示） | 复议条件 |
|---|---|---|---|---|
| D1 | 题材来源 | **纯设计推演**（8 域×3 层矩阵反推） | 题分布不贴真实使用频率；真实 badcase / 长尾 query 缺位 | 若需产出「体验分布」类结论，追加日志驱动的频率加权赛道 |
| D2 | 多轮形态 | **v1 固定 user_messages + 澄清题分支应答；v2 模拟用户独立赛道** | 分支应答依赖引擎支持（I1）；v1 多轮真实性有限 | v1 澄清题区分度不足时提前上模拟用户 |

### 默认采纳（细则 B/C 档，可复议）

## 一、分类原则

**P1 两轴正交：场景域 × 难度，能力维度不参与命名与配比。**
落地：8 域（navi/veh/chg/med/inf/svc/mem/sys，域边界与工具映射见 [esa-scenario-difficulty.md](esa-scenario-difficulty.md)）× L1/L2/L3；命名 `esa-<域>-L<层>-<序号>`；M1–M4 只出现在 rubric 的 `dimension` 字段。禁止用难度词命名维度或反之。
理由：维度与难度混用会让「变难了」和「换能力了」不可区分，矩阵失去解释力。

**P2 难度由算子机械判层，L3 的要件是认知性决策。**
落地：12 算子（O1 参数缺失–O12 时空外推）组合判层——L1=0 算子；L2=1–2 算子；L3=含 O6 能力外/O7 故障/O8 改主意/O9 策略之一，或 ≥3 算子叠加。L3 必须包含一个需要澄清、拒绝、降级或确认的决策点。pilot 后按实测通过率校层。
理由：「出题人觉得难」不可复核；算子清单使难度可审计、可复现、可校准。

## 二、题材与构造原则

**P3 题材从用户话术出发，覆盖优先于频率。**
落地：先写「座舱里用户会说的话」，再映射工具与状态；真实使用分布（见 esa-scenario-difficulty.md §2）锚定题材取材顺序与话术自然度，每域等量配比（12–17 题/域）锚定矩阵。禁止从工具能力反推堆砌凑数。
理由：从工具反推产出的是「为了考某工具编的指令」，偏离真实交互形态；等量配比保证短板域不被高频域淹没。

**P4 派生优先于手写。**
落地：L3 边界题从正主题派生（`removal_spec`：删工具/删参数/删返回字段，话术不变）；澄清题从 L1/L2 抹参数或改指代派生（`ambiguity_spec` 标注歧义元素与解决方式 internal/user）。手写只用于算子组合复杂的题。
理由：派生题与正主形成对照组（同话术、异环境），失败归因干净，成本减半。

**P5 golden run 是入库前置条件。**
落地：每题附带 GT 链路（`ground_truth.json`：工具+具体参数+参数链+期望效果），由确定性校验器重放真实 handler 验证可解，产出 `golden-run.json` 证据；不过不入库。完整合同与分级校验见 [esa-solvability-spec.md](esa-solvability-spec.md)。归因协议：重放通过的题，模型失败 = agent 责任；重放失败 = 题目/数据/工具问题，不进评测结果。
理由：题目自身的数据/工具契约 bug 会被误记为模型失败，污染全局结论。

## 三、判分原则

**P6 一票否决；认终态，不认路径。**
落地：`forbidden_changes` / `tool_forbidden` / `process_constraints` 任一触发 → 任务总分记 0。`tool_checks` 用 `any_tool` 容忍等价实现；`ordered_tools` 仅在顺序有业务含义时使用。**实现前置 I2**：引擎现状是分项归零（tool_forbidden→tool_use=0、状态类→state=0，总分仍是加权值），须补 verifier 总分归零逻辑后本原则才生效。
理由（D3）：车机场景下「改了不该改的状态+做对主任务」不可接受；路径白名单会误杀合法等价解。

**P7 四维权重按题型定，禁止全局单一配方。**
落地：execute 0.5/0.2/0.15/0.15；clarify 0.15/0.25/0.30/0.30；boundary 0.10/0.25/0.30/0.35；knowledge 0/0.25/0.30/0.45（顺序：state/tool_use/reply/judge）。
理由：边界题的正确答案是「说的话」，state 权重必须让位；统一配方会系统性压低认知可靠性题的区分度。

**P8 正则只抓硬特征，语义判断归 judge，条目必须原子化。**
落地：`reply_checks` 限于可正则硬特征（否定/承诺词、`min_matches` 候选数）；语义级判真进 `judge_criteria`，每条只判一件事。澄清题必写 `ambiguity_spec`，边界题必写 `removal_spec`（v1 作元数据供 judge 与互审，引擎不读）。
理由：正则判语义漏误判都说不清；judge 条目不原子化，一致率上不去（C4 门禁过不了）。

## 四、多轮与真实性原则

**P9 v1 多轮可复现优先，模拟用户不进主分。**
落地：固定 `user_messages` + 澄清题分支应答（agent 追问形态匹配→走应答分支）。**实现前置 I1**：确认/扩展引擎分支应答；不支持则用「双轮确认式」话术近似（轮 1 模糊指令、轮 2 预写澄清答案），题目卡片标注近似降级。LLM 模拟用户只进 v2 独立赛道。
理由（D2）：用户侧随机性进分数后，Pass^3 把模拟器方差算进模型头上，一致性指标失真。

## 五、指标与报告原则

**P10 Pass^3 是主口径。**
落地：k=3（Harbor `n_attempts=3`）；Pass^3=部署就绪度主指标，Pass@3 仅作能力上限参照，差值（稳定性债）单列。
理由：座舱是高频重复场景，单次成功不构成可用；单报 Pass@3 虚高。

**P11 矩阵为主，不设权威总分。**
落地：主报告 = 8 域 × 3 层 Pass^3 矩阵 + M1–M4 雷达 + 失败归桶（硬门禁/state 未达/澄清失误/幻觉编造）；总分只作参考行；效率（calls/tokens/时延）旁列不进分。
理由：单总分掩盖短板并提供刷分靶子；效率进分会诱导「少做事」策略。

## 六、质量门禁原则

**P12 三道关入库**：golden run（P5）→ 双人互审（指令歧义 / 判分点漏错 / 合法路径是否都被认）→ pilot 校准（强锚+弱锚 n=3，通过率落带）。全过才入 bench 配置。
**P13 test 集不出库**：48 题 test 放本地私有目录，bench 配置引绝对路径，不入 git；评分定义仅 verifier 可读，不进被测 agent 上下文。
**P14 judge 一致率门禁**：双 judge 一致率 < 85% 的条目改写后重测；`judge` 权重为 0 时删除 `judge_criteria`（引擎约定）。

## 七、演进原则

**P15 引擎只补判分缺口，不追仿真。**
优先级：I2 总分归零（P6 前置，正式跑分前必须完成）→ I1 分支应答（P9 前置，试点澄清题前）→ v2 `clarification_checks` → v2 模拟用户赛道。O7 故障题进 v1：环境已支持 faults 注入（reject/missing_field/response_lost，见 solvability spec E4）。
底线：**宁可缺一类题，不可出判不了分的题。**
